What the app is

ShipProof is a claim-audit ledger for a small software project. It presents a fixed, labeled synthetic completion claim — “All three authentication requirements are complete.” It lists the explicit requirements behind that claim, lets you link each requirement to named JUnit tests, reports the requirement as VERIFIED, FAILED, or UNVERIFIED, and reduces those results to one claim-audit outcome: CANNOT VERIFY, NOT READY, or LINKED CHECKS PASSED. A passing test is treated as narrow evidence, never as proof the whole feature works.

Requirements and mappings

Three fixed sample requirements and explicit requirement-to-test links. Links survive report imports; a link whose test disappears becomes MISSING.

Evidence

A conservative JUnit XML reader in the browser. No network, backend, account, or AI judgment. The bundled sample is declared synthetic.

Evaluation

One pure function applies the verification rule: any linked failure means FAILED; all linked checks must pass for VERIFIED; everything else is UNVERIFIED. A second step reduces those rows to the claim-audit outcome and the requirements that block the claim.

Output

A deterministic JSON readiness report built from the same evaluation the dashboard shows, including the claim-audit decision, blockers, explanations, and gaps.

One action, end to end

“Load sample evidence” is the shortest full path through the app: a click becomes parsed test results, an evaluated ledger, and the visible claim audit NOT READY with 1 verified / 1 failed / 1 unverified.

The same pure evaluator feeds the JSON export: src/export.ts calls evaluateLedger(state) and writes the resulting summary, decision, blockers, and per-requirement statuses. The visible claim audit and the downloaded report cannot disagree about a status or decision unless the state changed between them.

The all-pass contrast

Importing fixtures/all-pass.junit.xml makes every test case pass, but REQ-003 still has no linked evidence. The screen shows 2 VERIFIED / 0 FAILED / 1 UNVERIFIED and a NOT READY claim audit, with only REQ-003 blocking the claim. Linking one passing test to REQ-003 produces LINKED CHECKS PASSED; removing that link restores NOT READY. The suite's pass rate never decides the requirement — the explicit link does.

Reference route

Not a completed guided tour. This is a suggested 4-stop route for reading the code yourself. Each stop names a real file and a search anchor rather than a fragile line number.

Stop 1 — Where the click starts

src/ui.ts · search function buildHeader

The header renders the “Load sample evidence” button only while no evidence is loaded, wires its click to onLoadSample, and shows the import and export controls. The disabled export is explained by visible text, not color alone.

Stop 2 — From click to stored evidence

src/main.ts · search function loadSample

The controller sets a busy state, parses the bundled XML through parseJUnitReport, wraps the tests with an explicit synthetic source, and replaces the evidence. If parsing throws, the previous state is untouched and the error is rendered in an alert. src/junit.ts contains the conservative rules that reject malformed XML, namespaces, conflicting outcomes, and duplicates instead of guessing.

Stop 3 — Where a status is decided

src/domain.ts · search function statusFor

This is the whole per-requirement verification rule. A present FAIL wins, an empty check list is UNVERIFIED, all PASS is VERIFIED, and anything else — MISSING, SKIPPED, ERROR — falls through to UNVERIFIED. The requirement rows are built from this result, and tests/domain.test.ts pins the combinations.

Stop 4 — Where the claim-audit outcome is derived

src/domain.ts · search function summarize and function decisionFor

After every requirement is evaluated, summarize counts the statuses, calls decisionFor, and turns each non-verified row into a blocker with its ID, title, status, and reason. src/ui.ts · buildDecision presents that result as the claim audit above the counts. The JSON export consumes the same summary object, so the visible claim audit and the exported decision have one source.

Show the evaluation core 
function statusFor(checks: readonly CheckDetail[]): Status {
  if (checks.some((check) => check.outcome === 'FAIL')) {
    return 'FAILED';
  }
  if (checks.length === 0) {
    return 'UNVERIFIED';
  }
  if (checks.every((check) => check.outcome === 'PASS')) {
    return 'VERIFIED';
  }
  return 'UNVERIFIED';
}

Show the claim-audit core 
function decisionFor(
  failed: number,
  unverified: number,
  hasEvidence: boolean,
): ReadinessDecision {
  if (!hasEvidence) {
    return 'CANNOT_VERIFY';
  }
  if (failed > 0 || unverified > 0) {
    return 'NOT_READY';
  }
  return 'LINKED_CHECKS_PASSED';
}

A practice to reuse

The reusable move is turning a vague completion claim into one deterministic predicate, then testing the evidence combinations that could make it lie.

In this project the claim “this requirement is verified” became the predicate all linked checks pass, written once in statusFor and exercised in tests/domain.test.ts. The bundled sample makes the payoff visible: REQ-003's linked evidence simply does not exist, so a report full of passing tests still shows UNVERIFIED and the claim audit stays NOT READY. On another project, the same approach works for “done,” “safe to merge,” or “ready to ship”: name the observable evidence, define the rule in one place, and add the cases where missing or inconclusive evidence could otherwise be read as success.
